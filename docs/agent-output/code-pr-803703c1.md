## 1. Scope confirmation
This build proposal covers the core workflow for **FEAT-01 Guided Vehicle Inspection** and **FEAT-02 Defect Grounding & Notification** derived from the requirements summary (US‑101/102/201/202). The intent is to deliver:

1. A vehicle-specific, step-by-step inspection experience that enforces evidence capture on failed items and works offline.
2. FastAPI endpoints and persistence necessary to store immutable inspection records, defects, and evidence metadata.
3. Grounding logic that classifies critical defects, calls the grounding adapter, and drives notification fan-out with retry/fallback rules.
4. Front-end UX elements (Angular/Ionic) for the guided checklist, defect capture, and grounding banner/notification status.

Features outside FEAT‑01/02 (e.g., workshop repair, usage-based servicing) remain out of scope for this increment.

## 3. Test strategy

### Backend unit / integration tests (Pytest)

1. **Checklist loading** – ensures vehicle-type filtering, regulatory category enforcement, and odometer-first rule (US‑101).
2. **Inspection submission** – verifies:
   - All items require pass/fail outcomes.
   - Failed items require photo + ≥15-character description.
   - Immutable records (attempted updates rejected).
   - Manual odometer lower than previous reading requires explanation and is logged (US‑102).
3. **Offline sync deduplication** – same inspection payload retried offline only creates one inspection (idempotency token + fingerprint) (US‑102).
4. **Grounding evaluation** – when at least one defect severity `CRITICAL`, system:
   - Persists grounding event.
   - Calls grounding adapter with idempotency key.
   - Blocks trip start status on subsequent vehicle queries (US‑201).
5. **Notification fan-out** – success path (Graph email + Teams message) within SLA, plus fallback path when primary channel fails, ensuring logging + duty manager escalation within 5 minutes (mock clock) (US‑202).
6. **Defect classification client** – ensures APIM call uses managed identity headers, handles timeout by placing defect in “pending review” state but still grounds vehicle (US‑201).

### Frontend unit / component tests (Jest / Angular Testing Library)

1. `VehicleLookupPage` – prompts odometer before checklist, blocks invalid odometer entry.
2. `InspectionRunner` – enforces single-item focus, disallows progressing on failed item without evidence.
3. `EvidenceCaptureSheet` – ensures min description length + camera integration stub.
4. `GroundingBannerComponent` – renders persistent banner, accessible ARIA live announcement, blocks navigation.
5. `OfflineQueueService` – stores inspections offline, replays within five minutes after simulated connectivity restoration.
6. `GroundingStatusService` – displays notification attempts and fallback states.

## 4. Code review guidance

Reviewers should confirm:

1. **Data integrity**
   - Alembic migrations match defined SQL indexing (vehicle+timestamp unique constraints).
   - Evidence references include immutable blob version IDs; no raw photos stored in SQL.
   - Inspection records are append-only; any “amendment” goes through new record creation.

2. **Security & compliance**
   - All outbound calls (APIM, grounding adapter) use managed identity tokens; secrets not hard-coded.
   - Pydantic models validate and sanitize user-provided text to prevent injection (especially descriptions).

3. **Resilience**
   - Grounding adapter client retries with exponential backoff and logs failure to alert channel.
   - Notification dispatcher records every attempt, respecting 5-minute escalation rule.

4. **Offline behavior**
   - Front-end queue encryption (if required) or at least driver scoping (no cross-user data leakage on shared devices).
   - Sync endpoint deduplicates via idempotency token + fingerprint.

5. **Accessibility & UX**
   - Checklist UI supports one-handed use, proper keyboard navigation, and ARIA attributes.
   - Grounding banner cannot be dismissed by client-side hacks; server truth always wins.

6. **Testing completeness**
   - New logic covered by unit tests listed above; CI pipeline updated accordingly.
   - Mock external clients (grounding adapter, APIM, Graph) in tests to avoid real calls.
