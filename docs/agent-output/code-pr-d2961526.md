Fleet Inspection And Maintenance – Code Generation Plan

Based on the provided project context and intake documents, here is the initial code generation plan for the Fleet Inspection And Maintenance system. This plan is business-agnostic, parameterized, and all tunable values will be placed in config files. No secrets or environment-specific values are hardcoded.

## 1. Domain Model Derivation

Entities (from requirements and UX):

- Vehicle
- Inspection
- Checklist
- ChecklistItem
- Defect
- Evidence (Photo, Description)
- WorkshopJob
- Repair
- Part
- Release
- ServicePlan
- OdometerReading
- User (Driver, WorkshopController, Planner, ComplianceManager)
- Notification
- Competency (for release)
- AuditRecord

## 2. Config Structure

All environment, endpoint, and tunable values will be placed in config files, e.g.:

- config/default.json
- config/dev.json
- config/production.json

Example config keys:

- inspection.syncIntervalMinutes
- notification.retryCount
- notification.timeoutSeconds
- integration.fleetManagementApiBaseUrl
- integration.telematicsApiBaseUrl
- integration.trainingRecordsApiBaseUrl
- featureFlags.offlineCaptureEnabled
- audit.retentionYears

## 3. API Endpoints (parameterized)

All routes are derived from entity names and versioned via config:

- GET    /api/v{config.apiVersion}/vehicles
- POST   /api/v{config.apiVersion}/inspections
- GET    /api/v{config.apiVersion}/inspections/{id}
- POST   /api/v{config.apiVersion}/defects
- POST   /api/v{config.apiVersion}/workshop-jobs
- POST   /api/v{config.apiVersion}/repairs
- POST   /api/v{config.apiVersion}/releases
- GET    /api/v{config.apiVersion}/service-plans
- POST   /api/v{config.apiVersion}/notifications
- GET    /api/v{config.apiVersion}/audit-records

## 4. Database Schema (parameterized)

Table names and fields are derived from the domain model. Example (PostgreSQL syntax, but can be adapted):

```sql
CREATE TABLE vehicle (
  id UUID PRIMARY KEY,
  identifier TEXT NOT NULL,
  type TEXT,
  regulatory_category TEXT,
  status TEXT,
  last_odometer_reading INTEGER,
  last_service_date TIMESTAMP,
  created_at TIMESTAMP,
  updated_at TIMESTAMP
);

CREATE TABLE inspection (
  id UUID PRIMARY KEY,
  vehicle_id UUID REFERENCES vehicle(id),
  user_id UUID REFERENCES app_user(id),
  odometer_reading INTEGER,
  inspection_time TIMESTAMP,
  checklist_id UUID REFERENCES checklist(id),
  status TEXT,
  offline_captured BOOLEAN DEFAULT FALSE,
  sync_time TIMESTAMP,
  created_at TIMESTAMP,
  updated_at TIMESTAMP
);

CREATE TABLE defect (
  id UUID PRIMARY KEY,
  inspection_id UUID REFERENCES inspection(id),
  checklist_item_id UUID REFERENCES checklist_item(id),
  severity TEXT,
  description TEXT,
  evidence_photo_url TEXT,
  evidence_description TEXT,
  status TEXT,
  created_at TIMESTAMP,
  updated_at TIMESTAMP
);

CREATE TABLE workshop_job (
  id UUID PRIMARY KEY,
  defect_id UUID REFERENCES defect(id),
  assigned_to UUID REFERENCES app_user(id),
  status TEXT,
  created_at TIMESTAMP,
  updated_at TIMESTAMP
);

CREATE TABLE repair (
  id UUID PRIMARY KEY,
  workshop_job_id UUID REFERENCES workshop_job(id),
  labor_hours DECIMAL,
  parts JSONB,
  outcome TEXT,
  post_repair_check JSONB,
  released_by UUID REFERENCES app_user(id),
  release_time TIMESTAMP,
  created_at TIMESTAMP,
  updated_at TIMESTAMP
);

CREATE TABLE service_plan (
  id UUID PRIMARY KEY,
  vehicle_id UUID REFERENCES vehicle(id),
  projected_service_date TIMESTAMP,
  due_window_start TIMESTAMP,
  due_window_end TIMESTAMP,
  last_service_date TIMESTAMP,
  usage_rate DECIMAL,
  odometer_source TEXT,
  created_at TIMESTAMP,
  updated_at TIMESTAMP
);

CREATE TABLE notification (
  id UUID PRIMARY KEY,
  recipient_id UUID REFERENCES app_user(id),
  channel TEXT,
  outcome TEXT,
  attempt_time TIMESTAMP,
  message JSONB,
  created_at TIMESTAMP,
  updated_at TIMESTAMP
);

CREATE TABLE audit_record (
  id UUID PRIMARY KEY,
  entity_type TEXT,
  entity_id UUID,
  action TEXT,
  actor_id UUID REFERENCES app_user(id),
  timestamp TIMESTAMP,
  correlation_id UUID,
  details JSONB
);

CREATE TABLE app_user (
  id UUID PRIMARY KEY,
  name TEXT,
  role TEXT,
  competency JSONB,
  created_at TIMESTAMP,
  updated_at TIMESTAMP
);

-- Additional tables for checklist, checklist_item, odometer_reading, competency, etc.
```

```json
  ],
  "checklists": [
    { "vehicle_type": "Truck", "items": [ ... ] }
  ]
}
```

## 6. Application Layer (parameterized)

- All business logic references config values (e.g., sync intervals, notification timeouts).
- All entity names, field names, and routes are derived from the project context.
- No business-specific values are hardcoded; all are loaded from config or master data APIs.
- All secrets (API keys, DB credentials) are loaded from environment variables or secret stores.

## 7. UI Screens (parameterized)

Screen names and fields are derived from the UX mockups and requirements:

- SCR-01: Guided Vehicle Inspection
- SCR-02: Defect and Grounding
- SCR-03: Workshop Repair and Release
- SCR-04: Service Plan and Compliance

UI labels, checklist items, and validation rules are loaded from config or master data APIs.

## 8. Integration Layer

- All integration endpoints (fleet management, telematics, training records) are loaded from config.
- Timeouts, retries, and fallback behaviors are tunable via config.

## 9. Audit and Compliance

- All actions (inspection, defect, grounding, repair, release) are logged in the audit_record table.
- Audit retention period is set via config (e.g., audit.retentionYears).
